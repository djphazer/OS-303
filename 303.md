# OS-303 Processor
This is the firmware for a TB-303 CPU replacement, targeting Teensy++ 2.0 using PlatformIO. It uses the Arduino-compatible Teensy framework, so using Arduino IDE to build it also works - just open the `src/src.ino` file. Make sure you have the Teensy libraries installed in Boards Manager, select "Teensy++ 2.0" and set CPU Speed to 4 MHz.

The checked SysEx restore work is currently identified as
`v0.8.4-restore-test` until it completes on-device testing.

### v0.8.4 restore-test additions

- Complete 4 KiB EEPROM backup over MIDI SysEx, including settings, patterns,
  chains, and auxiliary data.
- Panel backup mode: hold **Back** at power-up, release, arm the recorder, then
  tap Back to transmit.
- Checked restore mode: hold **Time + Back** at power-up and play a prepared
  restore file over MIDI.
- Eight-LED backup and restore progress displays, distinct ready and error
  displays, and a three-flash completion indication.
- CRC-16 on every restore chunk and CRC-32 across the complete EEPROM image.
- Power-loss recovery markers, deferred settings/signature commit, and a
  bootloader escape using Write/Next.
- MIDI Thru suppression during backup and restore so realtime clock traffic is
  not mixed into these operations.

## Hardware
It should run on any AT90USB1286 microcontroller board with compatible pinouts, like the [MSW V0X DEI](https://michigansynthworks.com/products/os-303). The `src/pins.h` file contains the vital mappings between the Teensy pins and the TB-303 circuit pins; this could be edited/replaced for porting to a different chip. The driver code uses direct port manipulation for efficiency; more portable code using `digitalWriteFast()` is left commented out.

## Engine
A basic sequencer implementation has been hacked together on top of the core drivers, with patterns saved to EEPROM. It tries to be a faithful imitation of the original, but without as many limitations, plus some extra features. With this foundation in place, there is an opportunity to remake the 303 sequencer as you see fit...

## Update via MIDI SysEx
A basic bootloader enables updates via MIDI. Hold the "Write/Next/Tap" button on startup to enter the bootloader; 4 LEDs will light up solid - PITCH, TIME, FUNCTION, and A#. Use a program like Sysex Librarian or MIDI-OX to send the "update.syx" file from a PC, taking care to throttle the send speed... (if it fails, you might need to send it slower!)

## Pattern backup via MIDI SysEx

The optional `tools/os303_backup.py` utility reads all pattern, track, and
settings data from the OS-303's EEPROM over MIDI. Backup requests are read-only,
so receiving a malformed or interrupted backup request cannot alter the device.

Install the host-side MIDI dependencies:

```sh
python3 -m pip install -r tools/requirements-backup.txt
```

Connect both MIDI IN and MIDI OUT between the computer and OS-303, stop the
sequencer and external MIDI clock, then list the available MIDI ports:

```sh
python3 tools/os303_backup.py list
```

Use a distinctive portion of the interface name to create the backup:

```sh
python3 tools/os303_backup.py backup my-patterns.syx --port "Your MIDI Interface"
```

The utility produces a portable `.syx` capture and a verified raw `.bin`
EEPROM image. A saved SysEx file can be checked again later:

```sh
python3 tools/os303_backup.py verify my-patterns.syx
```

### Panel-only dump

A dump can also be initiated without sending a request from the command line:

1. Connect the OS-303 MIDI OUT to a computer and arm a SysEx recorder such as
   SysEx Librarian or MIDI-OX.
2. Switch off the OS-303.
3. Hold **Back** while switching it on.
4. Release Back when all eight numbered pattern LEDs illuminate. This is the
   armed backup mode and is distinct from the four firmware-update LEDs.
5. Start recording, then tap **Back** once to begin the dump. Each numbered LED
   represents 12.5%: finished sections stay solid while the active section
   blinks. All eight LEDs flash together three times when the dump is complete,
   then the unit continues into normal operation.
6. Save the capture as a `.syx` file and verify it with the command above.

Holding **Write/Next without Back** at power-up still enters firmware update
mode. If both happen to be held, the read-only backup takes priority.

### Validate and clean a recorder capture

Keep the original file from SysEx Librarian or MIDI-OX unchanged. A complete
panel dump contains 128 distinct OS-303 EEPROM messages and is about 5.5 KiB,
but a recorder may report more messages if it captured unrelated SysEx or
identical duplicates. MIDI clock and other non-SysEx bytes do not form part of
the backup. Do not delete messages by hand.

First inspect the raw capture:

```sh
python3 tools/os303_backup.py verify recorded-backup.syx
```

The command reports the total SysEx count, unrelated messages ignored, and
identical duplicates removed while checking that all 128 EEPROM chunks are
present and agree. Missing chunks, conflicting duplicates, malformed data, or
an unexpected EEPROM signature make the command fail instead of producing an
apparently valid backup.

Create a canonical, restore-ready copy with a new filename:

```sh
python3 tools/os303_backup.py prepare-restore recorded-backup.syx ready-to-restore.syx
```

This is the cleanup step: it extracts the one complete EEPROM image, orders
the chunks, adds per-chunk and full-image checksums, and writes two new files.
`ready-to-restore.syx` is always exactly 130 SysEx messages (about 5.9 KiB);
`ready-to-restore.bin` is the matching 4,096-byte EEPROM image. Keep the raw
capture as the source archive, and send only the restore-ready `.syx` file back
to the OS-303.

### Safe pattern restore

Use only the restore-ready file created above. Each restore chunk has a CRC-16
and the complete EEPROM image has a CRC-32; the firmware checks both before it
commits the restored settings.

The prepared file can be independently checked before transmission:

```sh
python3 tools/os303_backup.py verify-restore ready-to-restore.syx
```

To restore with SysEx Librarian or MIDI-OX:

1. Connect the computer's MIDI OUT to the OS-303 MIDI IN.
2. In the librarian, set the pause between played messages to **at least 500
   ms**. Real-hardware testing found shorter pauses unreliable. The prepared
   file has 130 messages and takes about 67 seconds.
3. Switch off the OS-303, hold **Time + Back**, and switch it on.
4. Release both buttons when the alternating numbered LEDs and solid Time LED
   show that restore mode is ready.
5. Play the prepared `ready-to-restore.syx` file. The numbered LEDs fill from
   1 through 8 as the transfer is written and checked.
6. All eight LEDs flash three times after full-image verification, then the
   restored settings and patterns load into normal operation.

If Function illuminates while a single numbered LED chases from 1 through 8,
the restore failed validation. Replay the prepared file from its beginning; a
new BEGIN message safely restarts the session. Do not send an original recorded
backup directly—the firmware accepts only the checked restore protocol in this
mode.

Restore messages are ignored during normal operation; EEPROM writes are
enabled only in the explicit power-on restore mode. Merely entering restore
mode writes nothing. Once a valid restore begins, a two-byte recovery marker
keeps the device in restore mode after any interruption or power loss. Replay
the same prepared file from its beginning to recover. The settings and EEPROM
signature are committed last, and the recovery marker is cleared only after
the complete image passes CRC-32 verification.

No ISP programmer is required for backup or restore after this firmware is
installed through the existing MIDI bootloader. An ISP programmer is only a
recovery tool for a damaged or missing bootloader.

### Restore SysEx protocol

OS-303 uses the non-commercial manufacturer ID `0x7D`. Restore files contain
one BEGIN (`0x58`), 128 DATA (`0x59`), and one END (`0x5A`) message. DATA
messages identify a 32-byte aligned EEPROM address and carry 7-bit-packed data
plus CRC-16/CCITT-FALSE. BEGIN and END carry the same CRC-32/IEEE for the full
4,096-byte image. Device status replies use command `0x5B`.

The firmware ignores restore commands during normal operation. Inside restore
mode, the state machine latches malformed input and requires a fresh BEGIN
before accepting more data. The first EEPROM chunk, containing settings and the
format signature, is held in RAM until every chunk and the full-image CRC pass.
The final two bytes of otherwise-unused auxiliary EEPROM are reserved for the
recovery marker and remain `0xFF` outside an active restore.

## Development
Building the firmware primarily uses the [PlatformIO](https://docs.platformio.org/en/latest/core/installation/methods/installer-script.html) toolchain. Run `pio run` from the repo root; the build process produces a `*.syx` file for use with the MIDI bootloader. You might have to run `pip install intelhex` once locally.

Protocol and recovery tests can be run without hardware:

```sh
python3 -m unittest discover -s tools -p 'test_*.py'
c++ -std=c++11 -Wall -Wextra -Werror tools/test_eeprom_restore.cpp -o /tmp/test_eeprom_restore
/tmp/test_eeprom_restore
```

If you fork the repo and _enable GitHub Actions workflows_ on your fork, the server will build it for you when code changes are pushed. Anyone logged in to GH can [download the artifact files](https://github.com/djphazer/OS-303/actions/workflows/firmware.yml).

More info for developers will be added to [the Wiki](https://github.com/djphazer/OS-303/wiki).
